## Deviations from the plan (and why)

1. **`ItemDetail` route gained `discoveryOutfitId?: string`** (not in the plan's literal param list). The `discovery_item_saved` analytics event needs `outfit_id`, and `ItemDetail`'s params only carried `itemId`/`fallbackItem`/`origin`. Threading the outfit id through as an extra optional param was the minimal way to satisfy the analytics requirement without a global store (forbidden) or a second lookup.
2. **`DiscoveryOutfitDetail` route gained `source?: 'deep_link'`** (not in the plan's literal param list) — needed to let the detail screen fire `discovery_deep_link_opened` with `resolved: true|false` under the plan's own chosen "route-then-resolve" architecture (the deep-link handler itself never fetches, so it can't know `resolved` — only the screen does, once its query settles).
3. **Added `isAuthedTreeMounted` stash/replay-on-login for `discovery-outfit`** — the plan's phase-09 requirements said "if the authed tree isn't mounted, do NOT navigate into it" but didn't spell out the mechanism. `DiscoveryOutfitDetail` only exists in `AppNavigator`'s logged-in branch, and the existing `onReady`-based replay only fires once per container mount (never again across a login transition in the same session) — without the extra `AppNavigator` `useEffect`, a link opened while logged out would be correctly *not crash*, but would also never resurface after the user signs in. Added the minimal fix.
4. **Split the two screen files into styles/state/sub-view companions** (`discoveryFeedStyles.ts`/`DiscoveryFeedStates.tsx`, `discoveryOutfitDetailStyles.ts`/`DiscoveryDetailStates.tsx`/`DiscoveryOutfitSummary.tsx`) to satisfy the "<200 LOC" guidance in phase 07/08 — the first draft of both screens ran 280/337 lines with inline styles + local subcomponents.
5. **Skipped `wardrobeService.ts` edit** — `cloneCommonItem` already existed; the plan flagged it as "if absent (grep first)" and it wasn't absent.
6. **Analytics wiring is direct `track()` calls**, not new `analytics.ts` wrapper functions — matches the simpler existing precedent (`item_detail_opened`, `wardrobe_item_deleted`, `favourite_try_on_tapped`) since none of the 6 new events need cross-file reuse or the kind of session-Set dedup that earns a dedicated wrapper (the one exception, "Saved" persistence, lives in the hook itself, not analytics.ts).
7. **`fallbackItem` passed to `ItemDetail` omits `category_code`/`layer_code`** from the Discovery item payload — `ItemDetailFallbackItem` (existing type) doesn't declare those fields and nothing in `ItemDetailScreen`/`ItemDetailReadPanel` reads them (title/image/common-badge only use `id`/`name`/`image_url`/`image_png`/`category`/`is_common_item`). Widening the shared fallback type for two unused fields felt like scope creep; flagging in case a future feature needs them.

**Note on the phase-09 "graceful fallback" requirement:** the plan's exact wording is "unresolvable outfit → navigate('Discovery') + an info toast … route-then-resolve + in-screen fallback CTA". I implemented this as: the deep link always routes to `DiscoveryOutfitDetail`; on a 404/unpublished outcome the screen shows its in-screen "no longer available" state (shared with the phase-08 feed-tap 404 case) with a "Browse Discovery" button; **tapping that button** is what fires the toast + `navigate('Discovery')`. I did not auto-fire the toast+navigate the instant the 404 resolves (that would remove the in-screen state phase 08 explicitly requires and would be jarring for a feed-tap 404 too, since they share the same code path). Flagging this interpretation for review — if the intent was an automatic redirect specifically for the deep-link case, that's a small follow-up (add an effect that acts on `notFound && source === 'deep_link'`).
