## Deviations from the plan (and why)

1. **`DiscoveryRepository.list()` extended with `is_enabled`/`season`
   filters** (file nominally owned by phase 02, used by phase 03). The plan's
   file-ownership table exists to prevent *parallel* phases from colliding;
   since I implemented 01→02→03→05 sequentially myself in one session, I
   extended the phase-02 repo method rather than duplicating a second query
   path in the phase-03 service. This also matches phase 03 step 2's own
   intent ("narrow in SQL by status/is_enabled/season ... filter trend_tags
   in Python") more literally than filtering everything in Python would
   have. `trend_tags` filtering stayed in Python per the JSON-portability
   rationale (SQLite vs Postgres `JSON_CONTAINS`/`@>` divergence).
2. **`tests/conftest.py`'s shared `db_session` fixture** — added
   `models.discovery` to its model-import list. This fixture is used by many
   *existing* unrelated test files; the phase-05 risk table called this out
   explicitly ("New model not in the SQLite create_all set of a copied
   fixture") — without the import, every `db_session`-based Discovery test
   would fail with "no such table". Purely additive, verified the rest of
   the `-m unit` suite (666 tests) is unaffected.
3. **One shared `SimpleRateLimiter(60)` instead of two instances** for the
   3 public read routes. Phase 03 step 3 said "copy the rate-limit helper
   verbatim, two `SimpleRateLimiter(60)` instances" — `trending_drop.py`'s
   two instances exist because its two routes are different tiers (60 vs
   20/min); all 3 Discovery routes are the same read tier, so one shared
   limiter is simpler (YAGNI) with identical behavior.
4. **Migration verification did NOT run against a live database** (see
   "Migration verification" below) — no local Postgres/Docker available in
   this session, and `.env`'s `DATABASE_URL` points at a live Railway
   production instance. Ran an isolated-SQLite DDL round-trip of the new
   migration's `upgrade()`/`downgrade()`/`upgrade()` instead (see below),
   plus the standard `Base.metadata.create_all()` model-level verification
   the test suite already relies on.
5. **`status_code=422` literal instead of `status.HTTP_422_UNPROCESSABLE_ENTITY`**
   in `routers/admin/discovery_outfits.py` — the installed
   FastAPI/Starlette emits a `StarletteDeprecationWarning` for that
   constant in this environment; switched to the literal `422` to match
   `routers/admin/trending_drops.py`'s existing convention (which never
   used the named constant for its 4xx codes) and to silence the warning.

## Migration verification (no live DB available)

- `alembic -c migrations/alembic.ini heads` → `discovery1a2b (head)` (single
  head, confirms correct parenting).
- Full alembic history **cannot** run end-to-end against a fresh SQLite in
  this repo today — an unrelated pre-existing migration
  (`f9c1a2b3d4e5_scope_user_hrid_uniqueness.py`, a Postgres partial-index
  `create_index`) is not SQLite-compatible, so `alembic upgrade head` from
  scratch on SQLite fails before it ever reaches `discovery1a2b`. This is a
  pre-existing repo limitation, not something introduced here.
- Instead, verified `discovery1a2b`'s own `upgrade()`/`downgrade()` in
  isolation: bound `alembic.operations.Operations` directly to a real
  SQLite connection and ran `upgrade() → inspect tables/indexes/unique
  constraint → downgrade() → inspect (empty) → upgrade() again → inspect`.
  Confirmed: both tables created with the documented columns, both indexes
  (`ix_discovery_outfits_status`, `ix_discovery_outfits_season`,
  `ix_discovery_outfit_items_discovery_outfit_id`,
  `ix_discovery_outfit_items_item_id`), the `uq_discovery_outfit_item`
  unique constraint, clean downgrade, clean re-upgrade.
- Also ran the model-level equivalent used throughout this test suite
  (`flask_db.metadata.create_all()` on a temp SQLite via the `db_session` /
  `threaded_db` fixtures) — 35 tests exercise the ORM models against the
  real column definitions.
- **Did not** run `alembic upgrade head`/`downgrade` against the live
  Railway Postgres in `.env` — no local Postgres/Docker daemon was
  reachable in this sandbox, and running migrations against a live
  production database without explicit operator sign-off would be an
  unreviewed, one-way change outside this task's authorization. Flagging
  this as an open item for devops/tech-lead before deploy.
